# Код-ревью

Ревью собственного кода перед передачей. Формат: проблема, почему это важно, что сделано.

---

## Блокирующие

### 1. Коллизии публичных идентификаторов заказов

```python
def next_public_id(db, prefix, model):
    count = db.scalar(select(model.id).order_by(model.id.desc())) or 0
    return f"{prefix}-{100000 + count + random.randint(1, 99)}"
```

Идентификатор собирается из максимального `id` плюс случайное число от 1 до 99. Два заказа, оформленных подряд в одной корзине, получают одинаковый `count` и с вероятностью около 1% совпадут полностью. Поле объявлено `unique`, значит второй заказ упадёт с `IntegrityError`, а пользователь увидит пятисотую ошибку на середине оформления.

На демо-данных не воспроизводится, потому что заказов мало. В продуктиве проявится в первый же день.

**Исправлено:** последовательный счётчик в транзакции, случайная часть убрана.

### 2. Нет отката транзакции при ошибке оформления

В `checkout` между `db.flush()` и финальным `db.commit()` выполняется до десятка операций: списание баллов, уменьшение остатков, создание записей согласования, выдача промокодов. Любое исключение в середине оставляет сессию в грязном состоянии, а следующий запрос в том же соединении может закоммитить частичные изменения.

FastAPI закрывает сессию в зависимости `get_db`, но без явного `rollback`.

**Исправлено:** `rollback` в `get_db` при исключении.

### 3. CORS с подстановочным origin и `allow_credentials`

```python
allow_origins=["*"], allow_credentials=True
```

Спецификация запрещает эту комбинацию: браузер отвергает ответ с `Access-Control-Allow-Origin: *`, если запрос идёт с учётными данными. Сейчас работает только потому, что токен передаётся в заголовке, а не в cookie. При переходе на httpOnly-cookie сломается молча.

**Исправлено:** `allow_credentials` выключается, когда origin подстановочный.

### 4. Секрет подписи токенов с рабочим значением по умолчанию

```python
jwt_secret: str = "dev-secret-change-in-production"
```

Если переменная окружения не задана, приложение поднимется с известным секретом, и любой сможет выписать себе токен администратора. Умолчание, которое молча работает в проде, опаснее отсутствующего умолчания.

**Исправлено:** при `ENVIRONMENT=production` приложение не стартует с дефолтным секретом.

## Существенные

### 5. Согласование не проверяет, кто согласующий

По ФТ-ЗАК.3 очередь согласования строится по руководителю сотрудника. Сейчас любой пользователь с доступом к экрану заказов может согласовать любую заявку, включая собственную.

**Исправлено:** проверка, что согласующий не является автором заявки; для роли HR согласование разрешено, для прочих — только по совпадению с руководителем.

### 6. Запросы N+1 в дашборде и каталоге

`dashboard` вызывает `balance()` в цикле по сотрудникам, каждый вызов делает отдельный `SELECT` по лотам. `item_out` для каждой позиции каталога отдельно считает остаток промокодов и число покупок. На семи сотрудниках и двадцати трёх позициях незаметно, на тысяче сотрудников — десятки секунд.

**Исправлено частично:** лоты и партии промокодов загружаются одним запросом и раскладываются по словарю. Полное устранение требует агрегатов на стороне СУБД — отмечено как задача, не блокирующая демонстрацию.

### 7. Хак с динамическим импортом

```python
all_codes = [s.code for s in db.scalars(select(__import__("app.models", fromlist=["Section"]).Section)).all()]
```

Писалось, чтобы обойти циклический импорт, но циклического импорта здесь нет. Строка нечитаема и ломает подсказки среды разработки.

**Исправлено:** обычный импорт.

### 8. Эндпоинт с паролями открыт без авторизации

`/api/auth/demo-accounts` отдаёт логины и пароли всех учётных записей любому. Для демонстрационного стенда это и есть цель, но в продуктовой сборке такой маршрут недопустим.

**Исправлено:** маршрут регистрируется только при `DEMO_MODE=1`, в README отмечено явно.

### 9. Отсутствие ограничений на размер ответа

Ни один список не имеет пагинации: каталог, заказы, аудит, сотрудники возвращаются целиком. Журнал аудита за год работы — это сотни тысяч записей в одном JSON.

**Исправлено:** `limit` и `offset` в списках Пульта, значение по умолчанию ограничено.

### 10. Нет ограничений длины строковых полей

Схемы принимают строки любой длины, модели объявляют `String(255)`. СУБД обрежет или упадёт в зависимости от диалекта: PostgreSQL выдаст ошибку, SQLite молча запишет.

**Исправлено:** `max_length` в схемах ввода.

## Замечания без исправления

### 11. Дублирование расчёта стоимости ДМС

Функция `family_price` существует и на сервере, и на клиенте. Это осознанный компромисс: клиент показывает предварительную стоимость до отправки формы, сервер считает окончательную. Риск расхождения есть, но альтернатива — лишний запрос на каждое изменение поля.

Отмечено в коде комментарием с обеих сторон.

### 12. Отсутствие ограничения частоты попыток входа

Эндпоинт входа не защищён от перебора. Для стенда несущественно, для контура обычно закрывается на уровне шлюза, а не приложения.

### 13. Работа с датами без учёта часового пояса

`date.today()` и `datetime.now()` используют время сервера. Для системы, где сотрудники в разных часовых поясах, сгорание баллов в полночь означает разное время для разных людей. Требует решения на уровне бизнес-правил заказчика, а не кода.

### 14. Миграции не заведены

`alembic` в зависимостях, но схема создаётся через `Base.metadata.create_all`. Для демонстрации достаточно, для контура нужна первая миграция и запрет автосоздания.

## Что в коде сделано правильно

Бизнес-логика целиком на сервере: клиент не может обойти проверку бюджета, лимита или прав, подменив запрос. Это проверяется прямым обращением к API в обход интерфейса.

Балльная механика выделена в отдельный модуль и не размазана по эндпоинтам. Приоритет списания, сроки сгорания и расчёт баланса лежат в одном месте и покрываются тестами независимо от HTTP-слоя.

Права описаны декларативной картой и применяются зависимостями, а не условиями внутри функций. Добавление роли не требует правок в эндпоинтах.

Журнал аудита пишется в тех же транзакциях, что и операции, — запись не может потеряться при откате.
